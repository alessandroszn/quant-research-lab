# Design note — Phase 6.2: Windows `.exe` and installer

Status: **approved 2026-11-13.** Deviations, if any, are listed at the end.

## Goal

Someone with a Windows PC and no Python can install Quant Research Lab, run every analysis, and
uninstall it cleanly. The build is produced by GitHub Actions from the locked dependencies, and
CI proves that the frozen program gives **the same results as the source**.

The roadmap fixes the approach:

- a PyInstaller **one-folder** build;
- an installer on top (Inno Setup);
- a sample analysis run end to end in CI;
- the stated known limits: a large bundle, a SmartScreen warning without code signing, and the
  Qt (LGPL) notices shipped.

Publishing a GitHub Release and choosing the project's licence belong to phase 6.3. They are not
part of this phase.

## What is built

### Bundle contents

One folder, `Quant Research Lab/`, built with Python 3.13, contains two programs that share the
same libraries:

| Program | Kind | Purpose |
|---|---|---|
| `QuantResearchLab.exe` | windowed (no console) | the desktop app (`qrlab_app.app:main`) |
| `qrlab.exe` | console | the CLI (`qrlab.cli:main_entry`), for scripts and for CI |

The folder also holds:

- `THIRD_PARTY_NOTICES.txt`;
- the Qt and PySide6 licence texts;
- `build-info.json`, which records the commit, the build date, the Python version and the
  locked package versions.

### Why one folder

- **LGPL compliance.** Qt's DLLs stay as separate files that a user can replace. That is the
  LGPL's requirement for dynamic linking, and a one-file build would hide the DLLs inside the
  executable.
- **Faster start.** One-file builds unpack to a temporary folder at every launch.
- **Fewer antivirus false positives.** Self-extracting executables trigger them more often.

### Deliverables

Each build produces:

- `QuantResearchLab-<version>-win64-setup.exe`: the installer;
- `QuantResearchLab-<version>-win64.zip`: the same folder, a portable version that needs no
  installation;
- `SHA256SUMS.txt`: hashes of both.

They are uploaded as **workflow artifacts**, kept for 30 days and visible only to people with
access to the repository. Attaching them to a GitHub Release is a 6.3 step and needs your OK.

## Installer (Inno Setup)

- **Per-user installation, no administrator rights** (`PrivilegesRequired=lowest`): it installs
  to `%LOCALAPPDATA%\Programs\Quant Research Lab`.
- **Shortcuts:** one in the Start menu, plus an optional desktop shortcut (unticked by default).
- **Before installing:** a page shows the disclaimer: research analytics, not investment advice.
- **Installer language:** English and Italian (Inno Setup ships both translations).
- **Version:** taken from `pyproject.toml`. A fixed `AppId` lets a new version upgrade the old
  one in place.
- **The uninstaller removes only the program folder.** It **never** touches workspaces, which
  hold the user's data, or the settings file `%APPDATA%\qrlab\qrlab-app.ini`. The installer's
  final page and the docs tell the user where that file is.

### Inno Setup licence

- Inno Setup is free. Its site says: "All commercial users of Inno Setup are requested to
  purchase a commercial license."
- This is a personal, non-commercial research project, so it qualifies as a free user. I will
  record this decision in the PR.
- Inno Setup is a build tool and is not shipped inside the program.

### Availability in CI

Inno Setup may no longer be preinstalled on future Windows runner images; the runner-images
project has open discussion about it. The workflow therefore installs a **pinned version**
explicitly and checks it before compiling.

## Program changes (library and app)

### 1. Code version in a frozen build (`experiments.runner`)

Today `_code_version()` asks `git` for the commit of the folder that contains `qrlab`. In a
frozen build that is wrong in two ways:

- There is no repository. If the program sits inside some other git checkout, which is the case
  in CI, `git` would report **that checkout's** commit.
- A windowed program that starts `git` makes a console window flash on screen.

The change, when `sys.frozen` is set:

- The record takes the commit and the dirty flag from the bundled `build-info.json`.
- `git` is never started.
- Records gain `"frozen": true`, so a reader knows where the code version came from.
- Builds from a dirty tree are refused, so the bundled commit always describes the shipped code
  exactly.

The package versions in the record still come from `importlib.metadata`. The build bundles the
metadata of `quant-research-lab` and every package the record lists; without it, that lookup
fails in a frozen program.

### 2. App self-test (`qrlab_app.app`)

`QuantResearchLab.exe --self-test <workspace>`:

1. opens the workspace through the real window, with dialogs that answer automatically and
   settings kept in memory, so the user's settings file is never touched;
2. runs every config in that workspace on its own screen, one after the other, through the
   worker thread;
3. exits with 0 only if every run ends with status `success`, and with 1 otherwise.

The window is never shown. CI sets `QT_QPA_PLATFORM=offscreen`, so the offscreen Qt plugin is
bundled. The mode contains no financial logic: it clicks the same buttons a user would.

## Build and checks in CI

A new workflow, `.github/workflows/app-build.yml`, runs on `windows-latest`.

**When it runs:**

- on a manual dispatch;
- on tags `v*`;
- on pushes to `main`;
- on pull requests that touch `packaging/`, the workflow itself, `pyproject.toml` or `uv.lock`.

It does not run on every PR, because a build takes about 10 minutes.

**Steps:**

1. Install the locked environment: `uv sync --locked --extra app --extra parquet --group build`,
   on Python 3.13.
2. Write `build-info.json`. The build fails if `git status --porcelain` is not empty.
3. Run PyInstaller with the committed `packaging/qrlab.spec`. It sets no UPX compression,
   excludes test and interactive modules, and lists the data and metadata it includes.
4. Generate `THIRD_PARTY_NOTICES.txt` from the licence files of every distribution in the
   bundle:
   - the build **fails if any bundled distribution has no licence text**, unless that
     distribution is on an explicit list with a reviewed text;
   - Python's own PSF licence is included.
5. **Same results as the source:**
   1. copy the six `configs/experiments/example_*.toml` and `examples/data/` into two
      temporary trees;
   2. run them with `uv run qrlab run` (source) in one tree and with `qrlab.exe run` (frozen)
      in the other;
   3. `packaging/compare_runs.py` checks that every output table is **exactly equal** and
      every scalar identical. Timestamps and the code-version block are ignored.
6. **GUI self-test:** run `QuantResearchLab.exe --self-test` on a workspace made of the
   examples, and check the exit code and a `record.json` per config.
7. Build the zip and the installer (Inno Setup, pinned), and write `SHA256SUMS.txt`.
8. **Installer round trip:**
   1. silent install into a temporary folder (`/VERYSILENT /CURRENTUSER /DIR=…`);
   2. run the **installed** `QuantResearchLab.exe --self-test`;
   3. silent uninstall;
   4. check that the program folder is gone and the test workspace is still there.
9. Upload the three files and record the bundle and installer sizes in the job summary.

## Repository layout

New folder `packaging/`, outside `src/`, so it is not part of the library:

- `qrlab.spec`: PyInstaller spec, one analysis per program and one shared folder;
- `installer.iss`: Inno Setup script;
- `build_info.py`: writes `build-info.json`, and refuses a dirty tree;
- `notices.py`: third-party notices from the installed distributions;
- `compare_runs.py`: compares the output folders of two runs;
- `README.md`: how to build locally and what the CI build checks.

## Dependencies

- **New dev-only group `build`:** `pyinstaller` (6.22, which supports Python 3.13), pinned
  through `uv.lock`; `pyinstaller-hooks-contrib` comes with it.
  - **Reason:** the roadmap's packaging tool.
  - **Licence:** GPL-2.0 with the bootloader exception, which allows shipping frozen programs
    under any licence.
  - Not a runtime dependency.
- **Inno Setup:** an external tool installed only in the CI job. It is not a Python
  dependency.
- The `app` and `parquet` extras are bundled. pyarrow is needed by the factor-zoo study's data
  reader.

## Tests

These run in the normal CI, with no build and no network:

- **Frozen code version:**
  - with `sys.frozen` set and a `build-info.json` next to the program, the record takes the
    commit from that file, marks `"frozen": true`, and never calls `git`; the test fails if a
    subprocess starts;
  - a missing or broken file raises a clear error;
  - non-frozen runs are unchanged.
- **`build_info.py`:** a hand-written expected JSON from fixed inputs, and refusal of a dirty
  tree.
- **`notices.py`:**
  - with fake distributions in `tmp_path`, licence texts are collected in a fixed order;
  - a distribution without one is reported by name;
  - the reviewed-exceptions list works.
- **`compare_runs.py`:**
  - two identical hand-made output folders pass;
  - a changed table cell, a missing output and a changed scalar each fail with a message that
    names them;
  - timestamps and code-version differences are ignored.
- **App self-test:**
  - `main(["--self-test", ws])` runs offscreen on a workspace holding the projection example
    and returns 0;
  - a workspace with an invalid config returns 1;
  - an empty workspace returns 1, because a self-test that tested nothing must not pass;
  - the user's settings file is not touched.

The build workflow is the integration test: frozen and source results compared, the GUI
self-test, and the installer round trip.

## Known limits (stated in the docs)

- **Size.** I estimate 350–500 MB installed and 120–200 MB for the installer (NumPy, SciPy,
  pandas, statsmodels, Matplotlib, pyarrow and Qt). CI reports the real figures.
- **No code signing.** Windows SmartScreen will show "Windows protected your PC" until enough
  people have run the file. The docs explain *More info → Run anyway* and how to check the
  SHA-256. Signing (a certificate or Azure Trusted Signing) is a paid service and goes in
  `docs/IDEAS.md`.
- **Antivirus.** False positives on PyInstaller programs happen. The one-folder build without
  UPX reduces the risk but cannot rule it out.
- **Builds are not bit-for-bit reproducible.** Executables carry timestamps. What is
  reproducible is the content: the locked versions, the commit in `build-info.json`, and
  results identical to the source.
- **Windows 10/11 x64 only.** macOS is later, and goes in `docs/IDEAS.md`.
- **No custom icon** in 6.2; the default PyInstaller icon is used. An icon goes in
  `docs/IDEAS.md`.

The project has **no licence file yet**. The bundle ships third-party notices, but nothing
grants rights over the project's own code. That fits a private repository now, but it must be

## Risks

- **PyInstaller and PySide6 6.12 or new NumPy/SciPy versions.** Hidden imports or plugins may
  be missing. The self-test and the source-versus-frozen comparison catch this. Fixes go in the
  spec, each with a comment saying why.
- **Exact equality between frozen and source.** Both use the same wheels on the same runner, so
  equality is expected. If a library's multithreading made the last digits vary, I would come
  back to you before loosening the check, rather than add a tolerance silently.
- **CI time.** About 10–15 minutes per build. That is why the build does not run on every PR.
