# Design note — Phase 6.1: desktop app `qrlab_app`

Status: **draft, awaiting approval.**

## Goal

A Windows desktop app through which someone who does not use the command line can:

- import a portfolio and see its X-ray and health checks;
- run every analysis the library offers;
- read the results;
- see where the data came from and which runs were made.

The app is a **thin layer over the experiment runner**: it edits and validates configs, runs
them in a worker thread, and shows the outputs the runner writes. It contains **no financial
logic**. Anything the app shows is computed by `qrlab` and recorded in the same
`record.json` as a CLI run, so an app run and a CLI run of the same config are identical.

Packaging as a `.exe` with an installer is phase 6.2, and is not part of this note.

## Principles

1. **One entry point.** The app calls `qrlab.experiments` (`validate_experiment`,
   `run_experiment`, `KINDS`). It imports only `qrlab.experiments` and `qrlab.reporting`, plus
   the standard library and Qt. A test enforces this.
2. **Logic outside the widgets.** The screens' state lives in plain Python view-model classes,
   with no Qt, that are unit-tested. The widgets only display them and forward clicks.
3. **Workspace on disk.** The app opens a folder with the usual layout:
   - `configs/`;
   - `data/` (git-ignored and private);
   - `results/`.

   Nothing is stored elsewhere except the list of recent workspaces (Qt settings).
4. **No network.** The app never downloads anything. Downloads stay explicit steps outside the
   app; a `qrlab fetch` command is already in `docs/IDEAS.md`. Reports open in the system
   browser from local files.
5. **Privacy.** Real portfolio files stay in the workspace's `data/` folder. The app never
   copies them elsewhere and writes no telemetry or logs outside `results/`.

## Screens

The navigation bar on the left shows:

| Screen | What it does | Kinds |
|---|---|---|
| **Home** | open or create a workspace; recent workspaces; disclaimer | — |
| **Portfolio** | X-ray and health checks: run the report, then show findings and the HTML report | `portfolio_report` |
| **Risk** | covariance, risk contributions, VaR/ES and their backtest | `risk_report` (new, 6.1b) |
| **Scenarios** | historical and hypothetical stress tests of the holdings | `scenario_analysis` (new, 6.1b) |
| **Projections** | savings or withdrawal plan, as a distribution of outcomes | `projection` |
| **Optimiser** | 1/N, minimum variance, risk parity, maximum diversification, HRP and maximum Sharpe, with constraints | `optimisation` (new, 6.1b) |
| **Backtests & studies** | backtests and the four studies | `backtest`, `study_*` |
| **Data** | raw files with source, dataset, download date, size, SHA-256 and terms; age of the newest vintage | — |
| **History** | every run (record.json and trial ledger): status, config hash, inputs, code version; open its outputs | — |

**Each analysis screen has the same structure:**

- **Configs of these kinds in the workspace (left):** buttons to create a new config from the
  kind's example and to duplicate one.
- **Config editor (centre):**
  - a TOML text editor with a *Validate* button, which shows the runner's error messages
    verbatim;
  - a *Run* button, active only for a valid config.
- **Results (right):**
  - every output table, with its in-sample / out-of-sample / descriptive tag shown as a badge;
  - scalars and figures (PNG);
  - *Open report* opens the HTML report in the system browser;
  - *Open folder* opens the output folder.

Form-based editing of parameters is not in 6.1, because a generic form generator for every kind
is large work. It is recorded in `docs/IDEAS.md`. The editor shows each kind's parameter names
and descriptions taken from its documentation.

### Long runs

- Runs execute in a `QThreadPool` worker. The window stays responsive and shows a busy
  indicator with the elapsed time.
- One run at a time per workspace, because the trial ledger is written once per run.
- Runs **cannot be cancelled** in 6.1: the runner has no cancellation hook. The user is told
  this before starting a run marked long, such as the studies.
- When the run ends, the results pane loads the new record. A failed run shows the recorded
  error.

### Language

- The interface is in **English and Italian**, chosen in the settings.
- All strings are in one table, as in `reporting.labels`.
- Reports keep their own language parameter.
- Numbers and dates follow the chosen language, through `reporting.formatting`.

## Library additions

### `qrlab.experiments.workspace`

Read-only queries that the app and the CLI share, so that the app needs no other `qrlab`
package:

- `list_configs(root)`: configs by kind, each with its validation status.
- `list_runs(root)`: records under `results/`, newest first, with status and hashes.
- `list_raw_files(root)`: raw-store files with their provenance and the age of the newest
  vintage. This wraps `data.store`, inside `experiments`, which may import `data`.
- `example_config(kind)`: the example TOML of a kind, used by *New from template*.

### New experiment kinds (6.1b)

The new kinds are thin adapters over tested library functions, like the existing ones. Each has
an example config on synthetic files and an end-to-end test:

- **`risk_report`:**
  - inputs: an asset-returns CSV and the portfolio weights;
  - parameters: estimator (sample, EWMA or Ledoit–Wolf), confidence, ES method and the VaR
    backtest window;
  - outputs: covariance, contributions to volatility and ES, effective number of bets, VaR/ES
    (historical, normal, Cornish–Fisher, filtered historical), and the Kupiec and
    Christoffersen backtests.
- **`scenario_analysis`:**
  - inputs: holdings, prices and the scenarios TOML (phase 3.2 format);
  - outputs: the scenario results per position and the risk summary.
- **`optimisation`:**
  - inputs: an asset-returns CSV;
  - parameters: method, constraints, covariance estimator and expected returns where needed;
  - outputs: weights, risk contributions and the in-sample label. The kind is descriptive and
    says that in-sample optimised weights are not a forecast.

Their exact parameter tables go in the 6.1b PR, following these specifications. No new
financial code is written: only adapters.

## Package and dependencies

- **Package:** `src/qrlab_app` in the same distribution, with entry point `qrlab-app`.
- **Layering:** a new test checks that `qrlab_app` imports only the standard library, PySide6,
  `qrlab.experiments` and `qrlab.reporting`.
- **New dependency `PySide6-Essentials`** (6.12, Qt for Python):
  - **Why:** the roadmap fixes PySide6. "Essentials" (QtCore, QtGui, QtWidgets) is enough, and
    avoids the 200+ MB of add-ons such as QtWebEngine.
  - **Where:** an **optional extra `app`** and the dev group, for the off-screen tests. The
    library does not need it.
  - **Licence:** LGPL-3.0, used as dynamically linked wheels. The 6.2 installer will ship the
    Qt licence notices.
  - **Size:** the Windows wheel is about 82 MB; the first `uv sync` is slow on this
    connection.
- **Rejected:** QtWebEngine for showing HTML reports inside the app. It is too large for the
  6.2 installer, and the system browser is enough.

## Tests

- **View-models** (no Qt, synthetic workspace in `tmp_path`):
  - config listing by kind;
  - validation errors passed through verbatim;
  - run state machine (idle → running → done / failed);
  - one run at a time;
  - result loading with tags;
  - history ordering;
  - raw-file listing with ages from a fixed clock;
  - language switch.
- **`experiments.workspace`:** hand-built workspaces (two configs, two records, three raw
  files) and their expected listings.
- **Off-screen smoke test** (`QT_QPA_PLATFORM=offscreen`, in CI on Linux and Windows):
  - build the main window and visit every screen;
  - run the `projection` example through the worker on a temporary workspace and wait for
    completion;
  - check that the results pane shows its tables and the HTML report file exists.
- **Layering test** for `qrlab_app`.
- **6.1b kinds:** hand-checked values, for example a two-asset contribution split, one
  hypothetical shock on a two-position portfolio and 1/N weights, plus end-to-end runs.

## Risks

- **GUI tests are brittle.** That is why logic lives in view-models; the Qt test only checks
  that every screen builds and one run completes.
- **Typing.** PySide6 ships stubs, but strict mypy may need narrow `ignore`s for Qt signal
  types. Each one is documented.
- **Scope.** Charts beyond the PNGs the runner already writes, form editors, cancellation and
  multi-run queues all go to `docs/IDEAS.md`.
- **Threading.** Only the worker calls the runner, and results return through Qt signals. The
  runner is never called from two threads at once.

## New dependencies

`PySide6-Essentials` (optional extra `app`, dev group). The reason is above; it needs approval.
