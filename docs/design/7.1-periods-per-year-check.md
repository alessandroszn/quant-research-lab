# Design note — Phase 7.1: check `periods_per_year` against the data

Status: **approved 2026-11-13.** Deviations, if any, are listed at the end.

This is the first of the gap-closing phases. They come from the methodology pages and the
corrected risk register (6.3b). One phase is done at a time, each with its own note:

| Phase | Gap | Risk register row |
|---|---|---|
| **7.1 (this note)** | `periods_per_year` is never checked against the data's frequency | Wrong annualisation |
| 7.2 | the `projection` kind's files carry no "not a forecast" note | Projection overconfidence |
| 7.3 | returns CSVs carry no price type (total vs price return) | Dividends / distributions |
| 7.4 | the `portfolio_report` kind is single-currency and runs no look-through | Currency errors, stale look-through |

## The problem

Every annualising function takes `periods_per_year` explicitly, with no default. That is
right, but nothing checks the value against the data. If monthly returns are passed with
`periods_per_year=252`:

- volatility is overstated by a factor of √(252/12) ≈ 4.58;
- the arithmetic mean is overstated 21 times.

No error is raised. The dates the series already carries could catch this.

## Rule

New public function `qrlab.core.require_periods_per_year(periods_per_year, index)`:

- **When it checks.** Only when `index` is a `DatetimeIndex` with at least two dates. It infers
  the frequency with the existing `infer_frequency`, from the median gap between dates.
- **When it skips.** It does not check, and accepts the value, in three cases:
  - the frequency cannot be inferred (irregular dates);
  - the index is not made of dates;
  - there are fewer than two observations.

  These cases are stated in the docstring: the check is a guard, not a guess.
- **The bounds.** If the frequency is inferred, the value must lie in its accepted range,
  inclusive:

  | Inferred frequency | Accepted `periods_per_year` | Why the range |
  |---|---|---|
  | daily | 250 – 366 | trading-day (250–262) and calendar-day (365–366) conventions |
  | weekly | 50 – 53 | 52 or 52.18 weeks a year |
  | monthly | 12 | — |
  | quarterly | 4 | — |
  | annual | 1 | — |

- **On failure.** It raises `ValidationError` with both facts. For example: "periods_per_year
  is 252, but the dates are monthly (median gap 31 days): use 12".
- **Return value.** The value as a float. It also checks that the value is a positive finite
  number, as today.

The value is still never chosen automatically. The function only refuses a value that
contradicts the dates. `CONVENTIONAL_PERIODS_PER_YEAR` stays a reference.

## Where it is applied

| Place | Series checked |
|---|---|
| every annualising function in `qrlab.metrics`: performance, relative, drawdown and capture ratios | the returns series passed in |
| `qrlab.stats.factor_exposures` | the excess-return series |
| `qrlab.lookthrough.tracking_error` | the fund's tracking series |
| `qrlab.backtest.summarize_backtest` | the result's net return series |
| the `risk_report` and `optimisation` kinds | the dates of the returns file, at run time |

Two places are **not** changed, because their periods are simulation steps, not dated
observations:

- `qrlab.simulation`;
- the `projection` kind.

## Compatibility

- No signature changes. The public API gains one function, so `docs/api/public-api.txt` is
  updated.
- The change turns a silently wrong result into an error. It goes in before 1.0.0, which is not
  yet published, and under the compatibility policy it would also count as a bug fix.
- Existing tests or examples that pair dated series with a contradicting `periods_per_year`
  will fail. Each one is listed in the PR and corrected: the test data, not the rule.

## Tests (hand-checked cases)

- **Monthly index:** 12 passes; 252 raises, naming "monthly" and 12; 4 raises.
- **Business-daily index:** 252, 250, 262 and 365 pass; 12 raises.
- **Weekly index:** 52 and 52.18 pass; 12 raises.
- **Quarterly** (4) and **annual** (1) pass; quarterly with 12 raises.
- **Skipped cases, accepted without a check:**
  - irregular dates (median gap 10 days);
  - a `RangeIndex`;
  - a single observation.
- **Errors, as today:** 0, a negative value, NaN, infinity and a boolean raise.
- **Integration:**
  - `annualised_volatility` on monthly data with 252 raises; with 12 it gives the
    hand-computed value;
  - `summarize_backtest` and `factor_exposures` raise on a contradicting value;
  - a `risk_report` config with `periods_per_year = 252` on the monthly example file fails
    validation at run time with the message.
- **Regression:** the full suite passes; any test that relied on a contradiction is corrected
  and listed.

## Risks

- **Real data with gaps.** Holidays or missing months may shift the median gap. The ranges of
  `infer_frequency` already allow for this: daily is 1–4 days, monthly 27–32. A series too
  irregular to classify is not checked rather than refused.
- **Breaking user code.** Code that passes a contradicting value now fails loudly. That is the
  point. The message says what to use.
