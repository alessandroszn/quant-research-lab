# Design note 12.1 — a form for each analysis

Status: **approved 2026-11-17; 12.1a built, 12.1b to follow.** First phase of Level 12
(`docs/design/levels-10-13-plan.md`).
The rule stays: **the app contains no financial logic.**

## The problem

To run an analysis in the app today, the owner edits TOML in a text box.

- **What each kind accepts** is spread over three places:
  - the kind's `parse` function (`require_keys` calls and checks);
  - its module docstring;
  - the hand-written list in `docs/guides/kinds.md`.
- **They can drift apart.** `kinds.md` lists only the top-level keys.
- **No form can be built** from what the code knows, because the code does not describe its
  keys: it only checks them.

## The change, in two steps

The phase is 14–20 h, so it lands in two parts, each with its own gate and merge.

- **12.1a — schemas in the library:** every kind describes its inputs and parameters. The
  description drives the structural validation and the guide.
- **12.1b — the form in the app:** built from the schema, next to the TOML editor, and writing
  the same config.

### 12.1a — parameter schemas (`qrlab.experiments.schema`)

**A schema** is a tree of frozen dataclasses: no Qt, no I/O.

**`Field`:** one key.

- `key`, `kind` (below), `required`.
- `help`: a short text in English and Italian, the app's two languages.
- `unit` where it means something (`"fraction"`, `"periods"`, `"days"`, `"years"`, `"currency
  units"`). Rates are fractions everywhere, as today.
- `choices`, `minimum`, `maximum` where they apply.
- **No defaults.** An optional key that is absent means "this feature is off", as today, and
  the help text says what that means. Nothing is filled silently.

**The field kinds** cover every key the 10 kinds take today:

| Kind | Example |
|---|---|
| `text`, `integer`, `number`, `boolean`, `date`, `datetime` | `title`, `window`, `confidence`, `sensitivity`, `start`, `generated_at` |
| `choice` | `language` (`it`, `en`), `flow_timing` |
| `currency`, `isin` | `base_currency`, the keys of `[parameters.holdings]` |
| `list` (of a scalar kind) | `percentiles`, `fund_assets` |
| `matrix` (a list of lists of numbers) | `correlation` |
| `table` (fixed fields) | `[parameters.risk]` |
| `map` (free keys of a stated kind, each a value of one schema) | `[parameters.proxies]` (ISIN → factor → beta), `custody` (account → table) |
| `records` (a list of tables) | `flows`, the `distributions` of a fund |
| `variant` (a key that selects the fields of the rest) | `strategy` by `name`, `engine` by `name`, `policy` by `type`, `[parameters.tax]` by `country` |

**`InputSpec`:** one input file.

- Its name, whether it is required, and its help.
- What it holds, for example "a price file (CSV or xlsx) read with its mapping", with the
  name of its companion input when there is one.
- The input groups (one file per free key, for example `holdings.<ISIN>`) are `map` inputs.

**`KindSchema`:** a kind's inputs and its `[parameters]` fields. `ExperimentKind` gains
`schema: KindSchema | None = None`, an addition with a default. A test requires every
registered kind to have one.

**What the schema decides, and what stays in `parse`.**

- **The schema, through `check_parameters(schema, parameters)`:**
  - unknown keys and missing required keys, at every level;
  - types, choices and ranges;
  - the variant's selector;
  - free keys of the right kind (an ISIN is a valid ISIN).

  It runs in `validate_experiment` before the kind's `parse`, and every error names the full
  path of the key: `[parameters.risk.backtest] window: an int >= 2`.
- **`parse` keeps the rules that tie keys together:** both-or-neither pairs, weights that sum
  to 1, a factor named in the proxies that must exist in the file. It keeps its own key
  checks too, so a library caller that skips the schema is still protected. The schema adds
  a first, uniform check; it removes nothing.

**The single source, enforced by tests:**

1. **The keys:** the schema's top-level keys equal the registry's `parameters` and
   `optional_parameters`, and its inputs equal `inputs`, `optional_inputs` and
   `input_groups`, for every kind.
2. **Every config passes:** every example config and every config built by the kinds' tests
   passes `check_parameters`. This shows the schema accepts what `parse` accepts.
3. **Removing a required key fails:** for each example config, removing any required field
   makes `check_parameters` fail and name that path. This shows the schema rejects what
   `parse` rejects.
4. **The guide is generated:** `docs/guides/kinds.md` comes from the schemas, through
   `scripts/kinds_guide.py`, with every nested key, its unit and its help. A test checks
   that the committed guide equals the generated one.

**The tax regimes** (Italy, Switzerland, custom) already list their own keys
(`TaxRegime.keys`). Each gains a `schema` (a `table`), and `[parameters.tax]` is a `variant`
over `country`.

### 12.1b — the form (`qrlab_app`)

**A Qt-free view-model, `FormModel`,** as the app's other screens have.

- It holds the values of one config by path, the errors of the last check, and which fields
  are shown. A `variant` shows the fields of its selected option; an optional `table` is
  shown when it is switched on.
- `from_config(schema, mapping)` and `to_config()` move between the form and the config's
  parameters.
- Each change runs `check_parameters` and shows its message on the field.
- Tested without Qt.

**The widgets** are one per field kind:

| Field kind | Widget |
|---|---|
| `text` | a line edit |
| `integer`, `number` | a spin box with the unit as suffix |
| `boolean` | a check box |
| `date` | a date edit |
| `choice` | a combo box |
| `table` | a group box |
| `map`, `records` | a list with add and remove |
| `matrix` | a small grid |
| inputs | a path field with "Choose…" (relative to the config, as today) |

The help text is the widget's tooltip, in the app's language.

**The experiment screen** gets two tabs on the same config, **Form** and **TOML**.

- **Switching tabs:**
  - from TOML to Form, the TOML is parsed and the form filled; a TOML that does not parse
    stays in the TOML tab with its error;
  - from Form to TOML, the form writes the TOML.
- **Saving** works as today, with *Save / Discard / Cancel* on unsaved changes.
- **The form writes TOML** with `tomli-w`, the writing half of `tomllib`.
  - **It is a new dependency**, in the `app` extra only. The reason, for the commit message
    and the CHANGELOG: correct TOML escaping of strings, dates and nested tables is easy to
    get subtly wrong.
  - `tomli-w` is small, pure Python, MIT-licensed, and by the author of `tomli`, which is
    the standard library's `tomllib`.
- **Comments:** TOML written by the form has none.
  - When a config with comments is saved from the Form tab, the app asks first, saying that
    the comments will be lost.
  - Saving from the TOML tab keeps the file as typed.
- **The help texts are in the schema:** `qrlab_app.strings` holds only the app's own words.

## Edge cases

- **A config with a key the schema does not know** (an old config, or a typo): the schema
  check names it. The form shows the TOML tab with the error, and never drops the key
  silently.
- **A kind without a schema:** the test forbids it, so it cannot ship. A plugin kind would
  open in the TOML tab only.
- **Very long maps** (dozens of ISINs): the list scrolls. There is no limit.
- **Round trip:** TOML → form → TOML gives the same parsed mapping for every example config
  (comments and key order apart). A test checks it.

## Tests

- **12.1a:**
  - the four agreement tests above;
  - one test per field kind for `check_parameters`: accepted values, every refusal and its
    message with the full path;
  - the variant selector; free keys of each kind;
  - the generated guide;
  - every existing kind test unchanged.
- **12.1b:**
  - `FormModel` without Qt: building it from each example config, editing, the errors, the
    variant switch, the round trip;
  - an off-screen smoke test that builds the form of every kind (as the app's smoke test
    does today) and saves one config;
  - the comment warning.

## Risks

- **Two checks of the same key:** the schema's and `parse`'s. Tests 2 and 3 keep them
  consistent. If they ever disagree, the stricter one wins and the test fails.
- **Effort:** the `portfolio_report` kind has many nested tables. Its schema is the largest
  part of 12.1a, so 12.1a lands before the form starts.

## Out of scope

- Field-level help that links to the methodology pages: plain text first.
- Forms for the portfolio and data screens: they already have their own.
- Generating `parse` from the schema: the semantic rules stay hand-written and tested.

## Effort

14–20 h, as planned: about 8–11 for 12.1a and 6–9 for 12.1b.

## Results and deviations of 12.1a (2026-11-17)

- **Built:**
  - `qrlab.experiments.schema` (the field kinds and `check_parameters`);
  - short constructors and the shared fields in `qrlab.experiments.kinds._fields`;
  - a schema for each of the 10 kinds, 277 fields in all; the portfolio report's is in
    `_portfolio_schema.py`;
  - `ExperimentKind.schema` and the check in `validate_experiment`;
  - the generated guide and its script.
- **Deviation: the schema check runs after `parse`, not before.** Dozens of tests and every
  user know `parse`'s messages; checking after keeps them first, while the schema still
  refuses whatever `parse` lets through. The form of 12.1b calls `check_parameters` directly.
- **Two field options added on the way:**
  - `also`: texts accepted besides a number, for `annual_cost = "ter"`;
  - `allow_inf`: +inf accepted, for the volatility-managed study's `leverage_caps`, where
    `inf` means no cap.
- **Finding: `backtest`'s optional `losses` was missing from the registry** since 11.5, so the
  skeleton config refused it. Fixed, in the CHANGELOG.
- **Where the schema is stricter than `parse`:** only where `parse` accepts what makes no
  sense. Examples: a text where a list is due (the momentum strategy's `assets` read as
  characters), numeric strings or booleans as percentiles, NaN or infinite weights, an empty
  account name, an EWMA decay outside (0, 1), which the estimator refuses later anyway. Each
  is refused at validation now, with the key's path. No existing config or test used them.
- **Where the schema is laxer than `parse`:** rules that tie keys or files together stay in
  `parse` (pairs, sums, names that must exist, whole-number windows written as floats, start
  before end), and so do bounds that only the run checks. The checks that `parse` leaves to
  the run are listed in IDEAS.
- **Tests:**
  - 54 tests of the check: every field kind accepted and refused, with the paths;
  - the agreement tests for the 10 kinds and the 16 example configs (registry keys, every
    example passes, removing each required key fails with its name);
  - 4 tests of the guide;
  - the whole suite runs every config through both checks.
