# Design note 12.3 — interactive charts

Status: **approved 2026-11-17; built (12.3a and 12.3b).** Third phase of Level 12
(`docs/design/levels-10-13-plan.md`). The rule stays: **the app contains no financial logic.**

## The problem

- **The app shows figures as pictures.** The results panel puts each PNG in a label: no zoom,
  no pan, no value under the cursor. A 20-year projection or a 10-year backtest cannot be read
  closely.
- **Most time series have no figure at all.** A backtest's value path, its weights over time
  and the risk report's VaR backtest are written as tables only. In the app they are rows of
  numbers.

## What the plan assumed, and what the code shows

The plan says "the runner already writes the data behind each figure; the app plots those
files". Checked against the code and the example outputs:

| Figure | Where | Its data in a file? |
|---|---|---|
| Projection fan (`fan_real.png`) | `projection` kind, and the report's projection section | yes, `fan_real.csv` |
| Portfolio value over time | `portfolio_report`, inside `report.html` | **no** |
| Cumulative TWR | `portfolio_report`, inside `report.html` | **no** |
| Drawdown | `portfolio_report`, inside `report.html` | **no** |

The four studies draw no figures. So the plan holds for one figure out of four, and the three
history figures of the portfolio report need their data written first. Plotting a file's
columns as they are is fine; computing a cumulative return or a drawdown in the app is not.

On the other side, several tables are dated time series already:

- `backtest`: `values.csv` (gross and net), `weights.csv`;
- `projection`: `fan_real.csv`;
- `risk_report`: `var_backtest.csv`.

## The change, in two steps

Each step lands with its own gate and merge.

### 12.3a — the report writes the data behind its figures (`qrlab`)

`portfolio_report` writes two more descriptive tables, built from the same series it already
draws:

- **`value.csv`:** the portfolio value in the base currency, by date (the valuation series of
  the "value over time" figure);
- **`twr.csv`:** by period, `cumulative_twr` and `drawdown`, the two series of the TWR and
  drawdown figures.

Two tables, not one, because the value has a row per valuation date and the TWR a row per
period: joined, they would fill each other with gaps. The flow markers of the value figure
stay in the static figure only; the flows are already in the report's tables.

What does not change:

- **every existing output is byte-identical:** the HTML, the figures and the other tables;
- **the records:** they list the two new files, which is the only change in `record.json`;
- **no kind gets a new figure.**

### 12.3b — a chart for every dated table (`qrlab_app`)

**A Qt-free `ChartModel`** decides what can be drawn and holds the readout logic.

- **Chartable:**
  - the index is all ISO dates (`YYYY-MM-DD`), strictly increasing;
  - at least 2 rows;
  - at least one numeric column.

  An index of row numbers is not a date, even though pandas would parse it as one: the check
  is on the text.
- **The lines:** one per numeric column, labelled with the column name as written. At most 8
  are shown at first. A table with more columns (weights of many assets) shows the first 8 and
  a list of tick boxes for the rest.
- **The readout:** for the date nearest the cursor, the date and each shown column's value,
  formatted in the app's language (`display.cell_text`, as the tables are). A missing value
  shows as a gap in the line and as "–" in the readout.
- **Nothing is computed:** no cumulation, no rescaling, no resampling. The values are those
  in the file.

**The widget** puts Matplotlib's Qt canvas in the results panel.

- `FigureCanvasQTAgg` with Matplotlib's own `NavigationToolbar2QT`: zoom to a rectangle,
  pan, back and forward, reset, and save as an image.
- A vertical line follows the cursor, and the readout shows below the chart.
- A table tab that is chartable gets two views, **Table** and **Chart**; other tables are
  unchanged. The PNG figures stay in their own tab, as the recorded outputs.
- The chart is drawn when its view is first opened, not when the result loads, so a result
  with many tables opens as fast as today.

**What it needs, and no new dependency:**

- **Matplotlib is already a dependency** of the library. The app's import rule
  (`tests/unit/test_architecture_app.py`) gains `matplotlib`, with the reason.
- **The app sets `QT_API=pyside6`** before importing the backend, so Matplotlib uses the
  binding the app uses.
- **The Windows build** stops excluding `matplotlib.backends.backend_qtagg` in
  `packaging/qrlab.spec` (its comment says the app only shows PNGs, which stops being true).
  The bundle grows by the backend module only: Qt is already in it.
- **The self-test** shows each result in the real results panel, and now also opens the Chart
  view of each result that has one. The CI's frozen build then proves that the backend is
  bundled.

## Edge cases

- **A dated index with times** (`2026-01-02 00:00:00`): not chartable. No output writes one
  today; if one does later, the test of every example output catches it.
- **Duplicated or unsorted dates:** not chartable, rather than drawn wrongly.
- **A column of text in a dated table** (a trade's side): left out of the lines.
- **Columns on very different scales** (a value and a weight in one table): drawn on one axis,
  as written. The tick boxes hide one. No second axis: choosing scales is analysis.
- **Long series** (a 25-year daily backtest): Matplotlib draws tens of thousands of points
  without help; nothing is thinned.
- **Dark theme:** the chart keeps Matplotlib's light style, like the PNGs.

## Tests

- **12.3a:**
  - hand-checked `value.csv` and `twr.csv` on the toy portfolio of the report's tests:
    `cumulative_twr` is $\prod (1 + r_t) - 1$, and `drawdown` matches `drawdown_series`;
  - every example's other outputs byte-identical to main; the records differ only by the two
    new files.
- **12.3b, `ChartModel` without Qt:**
  - chartable or not: ISO dates, row numbers, times, unsorted, duplicated, one row, no numeric
    column;
  - the lines and the first 8;
  - the nearest date: before the first, after the last, exactly on a date, between two dates;
  - the readout in English and Italian, with a missing value.
- **12.3b, off-screen:**
  - every example output: its dated tables get a Chart view, the others do not;
  - the toolbar is there; a simulated mouse move updates the readout; a tick box hides a line;
  - the chart is drawn only when its view opens.

## Risks

- **Matplotlib and PySide6 versions:** the Qt backend supports PySide6, and `QT_API` pins it.
  The off-screen tests run on Linux and Windows CI.
- **The frozen build:** if the backend is still not bundled, the self-test fails in CI before
  any release.

## Out of scope

- Charts of tables without dates (weights by asset, scenario results): bar charts would be a
  choice of presentation per table, a later phase if wanted.
- Two axes, log scales chosen by the app, comparing runs on one chart.
- Interactive charts inside `report.html`: it stays a static, self-contained file.

## Effort

8–12 h, as planned: about 2–3 h for 12.3a and 6–9 h for 12.3b.

## Results and deviations of 12.3a (2026-11-17)

- **Built as proposed:** `value.csv` and `twr.csv` in `portfolio_report`, from the same series
  the figures draw (`valuation.series()`, and the TWR returns with `drawdown_series`).
- **One detail decided on the way:** the value's column is `value_<currency>` (for example
  `value_EUR`), so the file states its currency, as every amount in the project does. Both
  tables have their index named `date`. `twr.csv` is written only when there is at least one
  period, as the two figures are drawn only then.
- **Checked by hand** on the example portfolio: the four values (9 990, 15 490, 15 290 and
  15 480 EUR); the cumulative TWR, $0.999 \times V_t / 14\,990 - 1$ from the second date,
  ending at the report's `twr_total`; and the drawdown, with the starting value as the first
  peak.
- **Byte identity against main:** in the two portfolio-report examples every existing file is
  identical (same SHA-256); the records differ only by the two new entries. The other five
  examples are identical.
- **Tests:** the hand-checked test above; the case without periods; the native-format test
  now lists the two new files.

## Results and deviations of 12.3b (2026-11-17)

- **Built as proposed:**
  - `qrlab_app.charts.ChartModel` (Qt-free);
  - `qrlab_app.chart_widgets.ChartView`, with Matplotlib's canvas and toolbar, the cursor
    line, the readout and the tick boxes;
  - the Table and Chart views in the results panel;
  - the self-test drawing every chart;
  - `backend_qtagg` no longer excluded from the Windows build.
- **Which example outputs are charts,** run and checked in a test, exactly as listed above:
  - `backtest`: `values`, `weights`;
  - `projection`: `fan_real`;
  - `risk_report`: `var_backtest`;
  - both portfolio reports: `value`, `twr`;
  - none for `optimisation` and `scenario_analysis`.
- **Small differences from the note:**
  - a missing value reads "—", the app's own missing mark (`display.MISSING`), not "–";
  - `QT_API=pyside6` is set once in `qrlab_app/__init__.py`, which runs before any module of
    the app imports Matplotlib;
  - Matplotlib's Qt backend and date helpers have no type hints, so mypy allows calls to
    untyped functions in `qrlab_app.chart_widgets` only (a `[[tool.mypy.overrides]]` entry
    with its reason); the rest stays strict.
- **Checked by eye:** the backtest's gross and net values in Italian, and the projection fan
  in English, rendered off-screen with the cursor on a date.
- **Tests:**
  - 11 Qt-free tests of `ChartModel` (every case of the note);
  - 13 off-screen tests: the charts of the 7 examples, drawing once and only when shown, a
    simulated mouse move and the readout, the tick boxes and the legend, one line without
    tick boxes, the results panel;
  - the app keeps 100 % coverage.
