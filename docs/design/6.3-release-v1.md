## Goal

Version **1.0.0** (milestone M6), consisting of:

1. a **stable public API** with a written compatibility promise;
2. a **documentation site**: guides, API reference, one methodology page per risk in the risk
   register, and the four studies;
3. a **release** on PyPI and GitHub, archived with a DOI on Zenodo;
4. a **combined working paper** of the four studies;
5. **launch material**: the README with figures, plus drafts of the website post and the
   LinkedIn post.

Several steps happen outside the repository, on accounts that are yours: GitHub visibility,
PyPI, Zenodo, GitHub Pages, your website and LinkedIn. For each one, I prepare everything and
tell you exactly what to click. **I publish nothing, and change no GitHub setting, without
your explicit OK at that moment.**

## Decisions for you

### D1. Licence of the project

There is none today. Before anything goes public there must be one.

| Option | In short |
|---|---|
| **BSD-3-Clause (recommended)** | NumPy, SciPy, pandas and statsmodels use it. Permissive and short. Compatible with the Qt LGPL in the Windows build. |
| MIT | Equally permissive and even shorter. Less usual in scientific Python. |
| Apache-2.0 | Permissive, with an explicit patent grant. Longer, and it needs a NOTICE file. |
| GPL-3.0 | Copyleft: derived works must stay open. Discourages use in industry. |

For the texts (documentation, study reports and working paper) I recommend **CC BY 4.0**:
anyone may reuse them, provided they cite you.

### D2. Making the repository public

A public repository is needed for three things:

- PyPI links that work;
- Zenodo's automatic archiving of GitHub releases;
- GitHub Pages without a paid plan.

Before you flip the switch, an **audit of the whole git history** runs (6.3c). Two facts to
know now:

1. **Your personal address in the history.** Your personal Gmail address is the author of
   132 commits; the other 63 use GitHub's noreply address. Public history shows it.
   - **(a) Keep it (recommended).** The study records cite commit hashes, so rewriting the
     history would break their reproducibility links. The old commits would also stay
     visible on the pages of the merged PRs.
   - **(b) Rewrite the history** to the noreply address (`git filter-repo`). This is
     destructive: every hash changes, the tags v0.1–v0.4 move, and it needs a force-push.
     The same caveat about PR pages applies.
   - **(c) Keep only the GitHub-facing address from now on.** Set
     `git config user.email` to the noreply address. This complements (a).
2. **`CLAUDE.md` is tracked** and would become public. It holds working rules and nothing
   personal. `AGENTS.md` is untracked and stays private.

### D3. Documentation tool

The roadmap names **Material for MkDocs**, but it reached **end of life on
2026-11-05**. Its successor, Zensical, is still a 0.0.x pre-release.

| Option | In short |
|---|---|
| **Sphinx + MyST-Parser + pydata-sphinx-theme (recommended)** | Mature, and the standard of NumPy, SciPy, pandas and statsmodels. Reads our NumPy-style docstrings natively (`napoleon`). MyST keeps the existing Markdown docs as they are. Builds the working paper's PDF too (LaTeX builder). |
| Zensical | Successor of Material for MkDocs, from the same team; supports mkdocstrings. Pre-1.0, with limited plugin support: a risk for a v1.0 release. |
| Material for MkDocs 9.7.x | Works today, but end of life: no fixes from now on. |

### D4. Name on PyPI

**`quant-research-lab`** is the current distribution name, and it is free on PyPI and
TestPyPI; the import name stays `qrlab`. `qrlab` is also free, but I would not reserve it with
an empty upload: PyPI discourages that.

### D5. Working paper: where it goes

- **Recommended: a PDF archived on Zenodo with its own DOI**, linked from the docs and the
  README.
- Optionally, SSRN or arXiv (q-fin). arXiv needs an endorser for new authors. That submission
  is yours to make; I prepare the files.

## Work, in four PRs (in this order)

### 6.3a — API freeze

**What is public.**

- **Part of the 1.0 API:**
  - every name in the `__all__` of a `qrlab` subpackage (341 names today);
  - the `qrlab` command line;
  - each experiment kind's config format;
  - the `record.json` format.
- **Not part of it:**
  - modules and names that start with `_`;
  - `qrlab_app`;
  - `packaging/`;
  - `research/`.

**Before freezing,** a review of the 341 names. Anything public by accident is made private or
renamed now, while that is still free. Every change is listed in the PR.

**Snapshot test.** `tests/unit/test_public_api.py` writes every public name with its kind and
signature to a text listing. It compares the listing with the committed
`docs/api/public-api.txt`.

- Any change to the public surface must update that file in the same PR, so it is always
  deliberate and visible in review.
- The generator is tested on a small hand-made module.

**Records.** `record.json` gains `"format": 1`, so future readers can tell the version.

**Compatibility policy,** in `docs/compatibility.md`:

- Semantic Versioning from 1.0.0;
- breaking changes only in a major release;
- removals first deprecated for at least one minor release, with a `DeprecationWarning`;
- results may change in a minor release only to fix a bug, and the CHANGELOG says so.

### 6.3b — Documentation site (tool per D3)

**Content.**

- **Getting started:**
  - installation: pip, or the Windows installer;
  - the first portfolio X-ray, on the synthetic example data.
- **Guides:**
  - the experiment configs and the CLI;
  - each experiment kind: what it computes, its parameters and outputs, and its sample tags;
  - the desktop app;
  - reproducing the four studies, including where to download the data and its licences;
  - the data sources and their terms.
- **Methodology:** one page per risk in the risk register (15 risks). Each page states the
  risk, a small example of how it goes wrong, how qrlab prevents it, and the tests that guard
  it, with links to the code.
- **The four studies,** as they are in `docs/studies/`.
- **API reference,** generated from the docstrings, with links to the NumPy, pandas and SciPy
  docs.

**Checks.**

- The docs build in CI with warnings treated as errors (`-W`).
- The examples in the guides run as doctests on synthetic data, so a guide never shows code
  that does not work.
- The external link check needs the network. It runs only on manual dispatch and before a
  release, not in the normal CI.

**Hosting.** GitHub Pages, deployed on release tags once the repository is public (D2).

**New dependency group `docs`:** Sphinx, myst-parser and pydata-sphinx-theme, if D3 goes as
recommended. The reasons go in the PR.

### 6.3c — Release and publication

**Files.**

- `LICENSE` (per D1), plus the licence expression in `pyproject.toml`.
- `pyproject.toml` loses the "Private :: Do Not Upload" classifier and gains the project URLs
  and keywords.
- `CITATION.cff` and `.zenodo.json`, so the GitHub "Cite this repository" button and Zenodo
  use the same metadata. A test checks that their version matches `pyproject.toml`.
- `CONTRIBUTING.md` (short) and `SECURITY.md` (how to report a problem).
- A **rewritten README.** The current one still says M1. The new one has status, install, a
  quickstart, figures from the studies (deterministic PNGs from the study records), and links
  to the docs, the paper and the citation.

**Pre-publication audit** (`scripts/audit_history.py`). It runs locally and prints no
sensitive values.

- It scans **every commit** of the history for:
  - files ever committed under `data/` other than the README;
  - spreadsheets, and CSV files outside `examples/` and `tests/`;
  - secret patterns (keys, tokens, private keys);
  - ISINs and IBANs.
- **Your real ISINs.** The script reads the ISINs of your real portfolio from the local,
  git-ignored `data/` folder. It checks that **none of them appears anywhere in the history**,
  and reports only counts and file paths.
- It is tested on a synthetic git repository built in `tmp_path`.
- The audit must be clean before I ask you to make the repository public.

**Release workflow** (`release.yml`), on a tag `v*`:

1. Build the sdist and the wheel (`uv build`) and check them.
2. Run the Windows build of 6.2.
3. Create a GitHub Release with the wheel, the sdist, the installer, the zip and
   `SHA256SUMS.txt`.
4. Publish to PyPI with **trusted publishing**, so no token is stored anywhere. The step waits
   in a GitHub environment `pypi` that **requires your approval**.

**First a dry run:** `1.0.0rc1` goes to **TestPyPI**. I then install it in a clean environment
and run the examples. Only after that comes `1.0.0`.

**Your steps, each with a short guide when we get there:**

- choose the licence (D1);
- make the repository public;
- add the trusted publisher on PyPI and TestPyPI;
- link Zenodo to the repository;
- enable GitHub Pages;
- approve the PyPI deployment.

### 6.3d — Working paper and launch material

**Working paper.** One paper on the four studies:

- abstract;
- a common methodology: data, inference with HAC errors and the bootstrap, multiple testing,
  and how results are recorded;
- one section per study, including the honest null results;
- limitations;
- a reproducibility appendix: commit, configs, data vintages and data licences.

The **tables and figures are generated from the study records**, never copied by hand. A
check confirms that every number in the paper matches its record. The PDF is built with the
docs tool's LaTeX builder (TeX Live installed in CI), then archived on Zenodo per D5.

**Launch drafts,** in English and Italian:

- the post for alessandrozanichelli.com;
- the LinkedIn post.

I hand them to you as files and do not commit them. You edit and publish them yourself.

## Tests

- **Public API:**
  - the snapshot generator, checked on a hand-made module (functions, classes, constants and
    signature changes);
  - the snapshot itself.
- **Records:** `format` is present and equals 1.
- **Docs:** they build with warnings as errors, and the doctests in the guides pass.
- **Citation files:** valid JSON for `.zenodo.json`; version and licence agree with
  `pyproject.toml`.
- **Audit script,** on a synthetic repository:
  - a committed data file, a spreadsheet, a fake token and a "real" ISIN are each found;
  - a clean repository passes;
  - the output never contains the ISIN values.
- **Paper:** every generated table matches the study records.
- **Release:** the TestPyPI dry run, then a clean install that runs the examples.

## Risks

- **Scope and time.** The roadmap gives 30–40 h. The working paper alone may take 15–20 h, so
  I expect 45–60 h in total. 6.3a–c can be released without 6.3d: v1.0 could ship first and the
  paper follow as 1.0.x documentation. Your call when we get there.
- **History privacy.** Covered by D2 and the audit; nothing goes public before both are
  settled.
- **Docs tool churn.** Material for MkDocs is already at end of life, hence D3.
- **Platform steps I cannot do.** PyPI, Zenodo and visibility need your accounts, and I never
  enter credentials. Trusted publishing avoids tokens entirely.

## Deviations

- **6.3a, two deeper modules are public.**
  - `qrlab.experiments.kinds`: `KINDS` is required by `run_experiment`.
  - `qrlab.experiments.workspace`.

  Both join the 341 names of the subpackages, for 513 lines in the listing.

  reproduced through their experiment kinds, whose configs are public.
- **6.3a, one rename from the review.** `qrlab.stats.FactorModel` became `FactorSet`, because it
  clashed with `qrlab.risk.FactorModel`. No other name changed. `EULER_GAMMA` and `TOLERANCE`
  stay public deliberately: they are documented constants of the functions that use them.
