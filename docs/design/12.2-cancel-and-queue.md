# Design note 12.2 — cancelling a run, and a queue

Status: **approved 2026-11-17; 12.2a built, 12.2b to follow.** Second phase of Level 12
(`docs/design/levels-10-13-plan.md`).
The rule stays: **the app contains no financial logic.**

## The problem

- **A run cannot be stopped.** The app runs it on a worker thread until it ends. A study with
  bootstraps takes minutes, and a wrong parameter means waiting for it to finish.
- **One run at a time per screen, with no order.** *Run* is refused while that screen is
  running ("Another run is in progress"). Nothing lines up a run on another screen after it.
- **A re-run destroys the earlier results first.** `run_experiment` deletes the output folder
  before the kind starts. A run that is interrupted (Ctrl+C in the CLI, or a crash) leaves a
  folder without `record.json` and no earlier results.

## What the plan said, and why this note differs

The plan proposed "a cancellation hook in the runner, checked between steps". The runner's
steps are short except one: `kind.run`, where all the time goes, inside library functions
(a bootstrap, a Monte Carlo, a walk-forward loop). A hook checked between the runner's steps
would wait for `kind.run` to end, which is the wait cancelling is meant to avoid. Passing the
hook into every long loop of the library would put app plumbing into pure functions.

**This note stops a run by running it in its own process and ending the process.** That stops
any computation at once, needs no change in the kinds, and keeps a crash in a run from
closing the app. The runner's part is to make an interruption safe: it never leaves partial
results that look complete, and it never loses the earlier ones.

## The change, in two steps

Each step lands with its own gate and merge.

### 12.2a — interruption-safe outputs (`qrlab.experiments.runner`)

**The run writes into a staging folder and moves it into place at the end.**

1. Outputs are written to `<parent>/.<name>.partial/`, next to the final folder.
2. `record.json` is written there last, as today.
3. Only then the staging folder replaces the final one:
   - the earlier folder, if any, is renamed to `.<name>.old`;
   - the staging folder is renamed to `<name>`;
   - the old one is deleted.

What this gives:

- **An interrupted run** (Ctrl+C, the process ended, a power cut) leaves the earlier results
  untouched. Only the staging folder is left behind.
  - On `KeyboardInterrupt` or `SystemExit` the runner deletes the staging folder itself, then
    lets the exception through.
  - A staging folder left by a killed process is deleted by the next run of the same config,
    and by the app when it ends a run.
- **A failed run is still a run:** the kind raised, the record says `failure`, and it replaces
  the earlier folder, as today.
- **`list_runs` skips folders whose name starts with a dot,** so a staging folder that already
  holds its `record.json` is never listed as a run.
- **The ledger (`trials.jsonl`)** gets a line only when a run is recorded, as today. A run
  stopped before its record is not a configuration tried: nobody saw its results, so it must
  not inflate the count used by the deflated Sharpe ratio.
- **The CLI** catches Ctrl+C, prints `cancelled: the earlier outputs are unchanged` and exits
  with code 130.
- **The outputs are byte-identical:** the same files, written to another folder first. The
  record holds no output path. The studies use only `output_dir.parent`, which is unchanged.
- **The `overwrite=False` check** still looks at the final folder.

### 12.2b — the queue in the app (`qrlab_app`)

**A Qt-free `RunQueue`** holds the app's runs in order and starts one at a time. One at a
time keeps the machine responsive, and the runs never compete for the same files.

| State | Meaning |
|---|---|
| waiting | in line |
| running | its process is working |
| done | recorded, status `success` |
| failed | recorded with status `failure`, or refused before starting (the message says why) |
| cancelled | removed while waiting, or its process was ended |

**Adding a run (*Run* on a screen).**

- The screen saves and validates first, and asks before replacing earlier outputs, as today.
- **The config file's SHA-256 is kept with the entry.** If the file has changed when the
  entry's turn comes, the run is refused (*failed: the config changed after it was queued*).
  What was queued is what runs.
- **Two entries may not write the same output folder:** the second is refused with a message,
  because it would replace the first one's results.

**Running.** The entry's turn starts a process (`multiprocessing`, the *spawn* method, the
same on every platform). The process calls `run_experiment(config, kinds=KINDS,
overwrite=True)` and sends back the record, or the error text if the config is refused.
The app checks the process every 200 ms with a `QTimer`; it never blocks the window.

**Cancelling.**

- **A waiting entry** leaves the line; nothing ran.
- **A running entry:** the process is ended (`terminate`, which on Windows ends it at once).
  The app then deletes the staging folder. The earlier results stay. The screen says
  *Cancelled; the earlier results are unchanged* (or *…; there were no earlier results*).
- **A run that ended just before the cancel** is kept as finished: its record is complete, so
  the entry shows *done* or *failed*, not *cancelled*.

**Where it shows.**

- **Each analysis screen:** *Run* adds the selected config to the queue; the message says
  *Waiting (2nd in line)* or *Running… 12 s*. A new *Cancel* button cancels this screen's
  entry. The results panel shows the run when it ends, if its config is still selected.
- **A new *Queue* screen**, between *Data* and *History*: every entry of this session with
  its config, kind, state, time and message; *Cancel* and *Open folder*. Finished entries can
  be cleared from the list (the runs stay in *History*).
- **Closing the window** with runs waiting or running asks *Cancel the N runs and quit?*.
  Today it refuses to close while a run is running.

**The queue lives in memory.** It is not kept between sessions; *History* is the lasting
record.

**The frozen program.** `multiprocessing.freeze_support()` is called first in
`packaging/launch_app.py`, which PyInstaller needs to start a child of the frozen program. The
Windows build's self-test already runs every example config through the real window, so with
this change it runs them through the queue and child processes of the frozen program. That is
the check that the frozen build can start a run.

**Cost:** each run starts a Python process, which imports pandas and the library: about 2–4
seconds on a desktop, against runs of seconds to minutes. Stated in the guide.

## Edge cases

- **A child process that dies without a word** (killed from outside, out of memory): the
  entry is *failed: the run's process ended unexpectedly (exit code N)*; the staging folder is
  deleted.
- **Cancel, then the process does not end within 5 s** (it should not happen with
  `terminate`): the app calls `kill`, and records that it did.
- **The workspace changes while runs are queued:** opening another workspace asks first, as
  for unsaved edits, and cancels the queue on *Yes*.
- **A config that is fine when queued but whose input file disappears before its turn:** the
  runner's validation in the child refuses it; the entry is *failed* with that message.
- **The same config queued twice:** refused by the output-folder rule.
- **Two app windows on the same workspace** (two copies of the app): not coordinated, as
  today. The staging folder makes a clash visible instead of silent: the second rename fails
  with a message.

## Tests

- **12.2a, the runner:**
  - outputs byte-identical to main for every example (the usual comparison);
  - a kind that raises `KeyboardInterrupt` mid-run: the earlier folder is unchanged, no
    staging folder is left, no ledger line, the exception goes through;
  - a stale staging folder is removed by the next run;
  - `list_runs` ignores a staging folder holding a record;
  - a failed run still replaces the earlier folder and is in the ledger;
  - the CLI's Ctrl+C message and exit code.
- **12.2b, `RunQueue` without Qt and without processes:** a fake starter with scripted
  results. One at a time, in order; cancelling a waiting and a running entry; finished just
  before cancel; config changed after queuing; the same output folder refused; a refused
  config; a process that ends with no result.
- **12.2b, with real processes** (marked `integration`): one example config through a child
  process gives the same `record.json` content as running it in-process (times apart); a run
  cancelled while it runs leaves the earlier results and no staging folder.
- **12.2b, the screens off-screen:** *Run*, *Cancel*, the Queue screen, closing with runs
  queued; the existing run tests, through the queue.

## Risks

- **`multiprocessing` in the frozen program on Windows:** the known need is
  `freeze_support()`. The CI self-test of the frozen build would catch a failure before any
  release.
- **The integration tests start processes:** slower (seconds each), so there are few of them.
  They run on both Linux and Windows CI.
- **Renaming folders on Windows** fails when a file inside is open (for example a report open
  in a browser may hold it). The runner then reports *cannot replace <folder>: <reason>*; the
  run's results are kept in the staging folder, and the message says where.

## Out of scope

- Progress percentages: a kind does not report its progress, and adding that would touch the
  library's loops, as above.
- Running several runs at once.
- Keeping the queue between sessions.
- Cancelling in the CLI other than Ctrl+C.

## Results and deviations of 12.2a (2026-11-17)

- **Built as proposed:** the staging folder, the swap at the end, the clean-up on
  `KeyboardInterrupt` and `SystemExit`, the removal of a stale staging folder (and of a stale
  `.<name>.old`), `list_runs` skipping folders whose name starts with a dot, and the CLI's
  exit code 130.
- **The ledger line is written after the swap,** not before the record as until now. The
  record's `configurations_tried` is computed first with `configurations_tried(...,
  including=hash)`, which gives the same number. So a run stopped before its outputs are in
  place leaves no ledger line.
- **When the swap fails** (a file locked on Windows), the earlier outputs are renamed back,
  the run's outputs stay in the staging folder, and the error names both folders. No ledger
  line is written: the run's results are not in place.
- **New public names:** `staging_dir(output_dir)` and `STAGING_SUFFIX`, which the app needs in
  12.2b to delete the staging folder of a run it ends.
- **Tests:**
  - an interrupted re-run (`KeyboardInterrupt` and `SystemExit`): the earlier outputs are
    byte-identical, no staging folder, one ledger line;
  - an interrupted first run leaves nothing and no trial;
  - a stale staging folder and a stale `.old` folder are removed by the next run;
  - a failed run replaces the earlier outputs and is a trial;
  - a swap that fails, with and without earlier outputs;
  - `list_runs` skips staging, replaced and hidden folders, but not a dotted name;
  - the CLI's code 130 and message.
