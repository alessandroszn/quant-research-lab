# Design note — Phase 5.2 `qrlab.experiments` and `qrlab.cli`: the single entry point

Status: **approved 2026-11-12.** Deviations, if any, are listed at the end.

## Goal

Every analysis or study becomes a **TOML config** that one runner executes headless and
reproducibly. Three callers use the same runner and contain no financial logic of their own:

- the CLI, `qrlab run <config>`;
- scripts;
- the desktop app (6.1).

Each run writes a **record** that says what was tested, on which data (with hashes), with
which parameters, how many configurations were tried, which results are in or out of sample,
and with which code version. The record is what makes a result checkable, and the trial count
feeds the deflated Sharpe ratio (5.1).

## Config file

```toml
[experiment]
name = "walk-forward-minvar"        # also the default output folder name
kind = "backtest"                    # a registered experiment kind
hypothesis = "Minimum variance beats 1/N after costs out of sample"  # or "descriptive"
seed = 20261112                      # required by kinds that use random numbers

[inputs]                             # local files only, relative to the config file
returns = "../data/returns.csv"

[parameters]                         # kind-specific, validated by the kind
...

[output]
directory = "../results/walk-forward-minvar"   # default: results/<name>, git-ignored
```

- **Required fields.** Every table and every key a kind declares is required. Unknown keys
  raise, so a typo cannot be silently ignored.
- **`hypothesis`** is required. Descriptive analyses, such as a portfolio report, say
  `"descriptive"`.
- **Inputs** are local files only. The runner never downloads; fetching data stays a separate,
  explicit step (`docs/IDEAS.md`). Each input is hashed (SHA-256) before the run, and a file
  that changes during the run raises.

## Runner (`qrlab.experiments`)

- **Kinds** are registered with a name, a parameter schema (required keys, types and
  allowed values) and a run function that receives the validated config and returns an
  `ExperimentOutput`:
  - tables, as named DataFrames written to CSV;
  - figures (PNG);
  - an optional HTML report;
  - scalar results.

  Every table and scalar is tagged `"in_sample"`, `"out_of_sample"` or `"descriptive"`, and
  the record keeps the tags.
- **`run_experiment(config_path, *, overwrite)`:**
  1. validates the config;
  2. hashes the inputs;
  3. runs the kind;
  4. writes the outputs and `record.json` into the output directory.

  An existing output directory raises unless `overwrite=True`, which is explicit.
- **Record (`record.json`):**
  - experiment name, kind and hypothesis;
  - the config verbatim, with its SHA-256;
  - inputs (path as given, resolved path, SHA-256, size);
  - parameters and seed;
  - outputs, with their sample tags and file hashes;
  - the code version: the qrlab version, the git commit and a dirty flag when available, the
    Python version and the core package versions;
  - start and end times (UTC);
  - status (`success`, or `failure` with the error message, in which case the record is still
    written).
- **Trial ledger.** Each run appends one line to `trials.jsonl` in the experiment's parent
  output folder. The line holds the experiment name, the config hash (excluding `[output]`),
  the time and the status.
  - The **number of configurations tried** is the number of distinct config hashes recorded
    under that name, and it is written into the record.
  - Re-running the same config does not inflate it.
  - Deleting the ledger is the user's choice, and the docs say that doing so hides trials.
- **Reproducibility.** The same config on the same inputs gives identical outputs, byte for
  byte except the times in the record. A test checks this.

## Experiment kinds in this phase (3)

| Kind | Inputs | Parameters (all required) | Outputs |
|---|---|---|---|
| `portfolio_report` | broker export, CSV mapping, prices, instruments TOML, check config | base currency, language, flow timing, price age, checks on or off | HTML report (2.3–2.5), check results (descriptive) |
| `backtest` | asset returns CSV (with a declared mapping) | strategy (`buy_and_hold`, `trend`, `momentum`, `walk_forward_optimisation` with a 4.2 method), execution lag, policy, costs, taxes, initial weights and value, periods per year | gross and net paths, summary (out-of-sample tag for walk-forward), trades |
| `projection` | none, or a returns CSV for `log_moments` | engine, plan (3.3), paths, seed, goal | summary, sensitivity, fan chart |

Each kind is a thin adapter: it parses parameters, loads files with the existing parsers
(1.2, 2.1) and calls library functions already tested. More kinds (risk, scenarios,
optimisation comparison, the studies in 5.3) follow the same pattern as they are needed.

## CLI (`qrlab.cli`)

The CLI uses the standard library's `argparse`, so it adds no dependency. Entry point:
`[project.scripts] qrlab = "qrlab.cli:main"`.

- `qrlab run <config> [--overwrite]` runs a config and prints the output folder and the record
  summary.
- `qrlab validate <config>` checks the config and the inputs without running.
- `qrlab kinds` lists the registered kinds with their parameters.
- **Exit codes:** 0 for success, 2 for a config or input error (with the message), 1 for a run
  failure (the record is still written).

## Layering

New packages at layer 7:

- `experiments`: may import every library package (`core` to `reporting`);
- `cli`: imports only `experiments`;
- `experiments` and `cli` do not import each other's internals beyond that.

The app (6.1) will import only `experiments` and `reporting`.

## Personal data

- Outputs go under `results/` by default, which is git-ignored.
- The record stores paths and hashes, never file contents.
- Examples and tests use synthetic files only.
- The docs remind the user that records of real portfolios are private.

## Tests

| Case | Expected |
|---|---|
| A known input file containing `abc` | SHA-256 `ba7816bf…20015ad` recorded |
| The same config run twice (`overwrite=True`) | identical outputs; trial count 1 |
| One parameter changed, then run | trial count 2; the ledger has 3 lines |
| `[output]` changed only | same config hash, so the trial count is unchanged |
| An unknown key, a missing key or an unknown kind | `validate` fails with the key named; exit code 2 |
| A missing input file | exit code 2 |
| A kind that raises during the run | record with `status = "failure"` and the message; exit code 1 |
| An existing output folder without `--overwrite` | raises; nothing is overwritten |
| `portfolio_report` on the synthetic example files | the same HTML as `examples/portfolio_report.py` |
| `backtest` walk-forward | outputs tagged `out_of_sample`; the summary matches calling the library directly |
| `projection` with a seed | the same summary as calling `simulation` directly |
| CLI `kinds` | lists the three kinds |

## Edge cases

- **Paths:** paths with spaces and non-ASCII characters (Windows); relative paths, resolved
  against the config file's folder.
- **Interrupted runs:** if the process is interrupted halfway, the record is written last, so a
  folder without `record.json` is visibly incomplete.

## Risks

- **Config sprawl.** Each kind owns its schema, and unknown keys raise.
- **Trial counts can be gamed** by renaming experiments. The record shows the name and the docs
  say so; honesty here is a discipline, not a guarantee.
- **Records of real portfolios** contain paths and amounts. They stay under the git-ignored
  `results/` folder.

## New dependencies

None. `tomllib`, `argparse`, `hashlib` and `json` are in the standard library.

## Effort

15–20 h (roadmap). Two PRs:

- (a) the config, schema validation, registry, hashing, record, trial ledger, runner and CLI,
  with a test kind;
- (b) the three kinds, example configs on synthetic data under `configs/experiments/`, an
  integration test that runs them through the CLI, and docs.

## Deviations from the approved note

- **`cli` may import `core`** as well as `experiments`, to catch `QrlabError` for exit code 2.
  The app rule (only `experiments` and `reporting`) is unchanged.
- **Records are JSON-like.** `RunResult.record` is the parsed content of `record.json`.
- **`portfolio_report`, version 1.**
  - Single-currency only: an amount in another currency fails the run with a clear message.
    FX inputs are listed in `docs/IDEAS.md`.
  - The valuation dates are the price-file dates from the first transaction on.
  - Look-through, risk and projection inputs are not wired yet; the report says "not computed"
    for those sections.
  - The provenance retrieval time of a local file is its modification time (UTC), so the same
    file gives the same report.
- **`backtest` returns** are read with an explicit `returns_format` table: date column, date
  format, delimiter and decimal separator. Rule-based strategies are tagged `in_sample`,
  because their rules may have been chosen after seeing the history. `walk_forward` is tagged
  `out_of_sample`.
- **`projection`** states its assumptions in the config: per-period log-return mean and
  volatility per asset, plus a correlation matrix. `rebalance_every = 0` means never.
- **Synthetic example inputs** live in `examples/data/`, and the configs are in
  `configs/experiments/`.
