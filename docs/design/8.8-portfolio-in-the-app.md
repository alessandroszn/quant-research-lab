# Design note — Phase 8.8: a portfolio built in the app

Status: **approved 2026-11-15.** Deviations, if any, are listed at the
end. It replaces 8.1 (`docs/design/8.1-first-real-run.md`) as the next step of Level 8.

## Why

8.1 assumed that the owner's broker export would drive the first real run. There is no such
export, and there should not need to be one. qrlab is a research lab that anyone can use with
their own files:

- **The portfolio is described by the user,** in the app, not imported from a broker.
- **Market data come from public sources:** downloaded by qrlab where the source's terms
  allow it, and by hand where they do not.
- **A broker export stays possible.** It becomes one way in among others, through the
  existing mappings.

Nothing about one person's account goes into the repository, as before.

## What exists today

- **Library.**
  - Transactions are read only through a broker mapping
    (`qrlab.portfolio.parse_broker_csv`, `BrokerMapping`).
  - Prices are read through a CSV mapping (`qrlab.data.user_csv`).
  - Instruments come from a TOML file.
  - `TransactionKind.TRANSFER_IN` already brings units in at a stated cost.
- **App.**
  - Screens: Home, the analysis screens (a TOML editor with Validate and Run), History, Data
    and Settings.
  - A portfolio can only be described by writing the files by hand.

## Design

### 1. Library: a native transactions file (`qrlab.portfolio.native`)

**One fixed CSV layout,** written and read by qrlab, so no mapping is needed:

- **Columns:** `id, trade_date, kind, account, isin, quantity, price, price_currency, amount,
  amount_currency, fees, fees_currency, taxes, taxes_currency, fx_counter,
  fx_counter_currency, note`.
- **Values:**
  - UTF-8, comma-delimited;
  - ISO dates;
  - dot decimals, no thousands separator;
  - `kind` is the `TransactionKind` value (`buy`, `transfer_in`, …);
  - rows in ascending date order;
  - amounts signed as in the library, with empty cells for fields a kind does not use.
- **Functions:**
  - `NATIVE_MAPPING`, a `BrokerMapping` constant, so reading goes through the same validated
    path as a broker export;
  - `write_native_csv(transactions) -> bytes` writes the file; numbers are written from their
    `Decimal`, never a float.

**The report kind** gains `transactions_format = "native" | "mapped"`, a required parameter,
so the convention is never silent:

- `"native"`: no `transactions_mapping` is allowed;
- `"mapped"`: `transactions_mapping` is required, as today.

Existing configs gain the one line `transactions_format = "mapped"`. A missing key raises with
that hint.

### 2. Starting from what you hold today

Someone who does not have their full history can declare a **starting position**: one
`transfer_in` per fund, on a start date, with units and cost per unit, plus a cash
`deposit`. The library already handles this. The report then:

- measures TWR and MWR from the start date only, and its notice says so;
- uses the declared cost for unrealised and realised gains and for the Italian tax position;
- says the cost was declared, not taken from trades.

### 3. App: a "Portfolio" screen

The screen only edits tables and calls library functions, so the app keeps no financial
logic.

- **Portfolios** live in the workspace, one folder each:
  `portfolios/<name>/transactions.csv` and `instruments.toml`. `portfolios` joins
  `WORKSPACE_FOLDERS`.
- **Transactions table:**
  - add, edit and delete rows;
  - `kind` is picked from a list, and only the fields that kind uses can be edited;
  - a "starting position" helper adds a `transfer_in` row per fund and a deposit.
- **Instruments table:** ISIN, name, type, asset class, currency, TER, distribution,
  domicile, replication, benchmark and `as_of`. The ISIN check digit is checked by the
  library.
- **Validate** writes the files and reads them back through the library (`NATIVE_MAPPING`,
  the instruments loader, the ledger). It shows every error with its row and column, in the
  app's language.
- **Create report** writes `configs/<name>-report.toml` from the `portfolio_report`
  template, with the portfolio's files, `transactions_format = "native"` and the price files
  chosen on the Data screen. It then opens on the report screen, where Validate and Run work
  as today.
- **Prices and holdings files** are added on the Data screen:
  - "Import a downloaded file" copies a file into the raw store unchanged, with provenance
    (`qrlab.data.user_csv.import_local_file`, which exists);
  - the file's mapping is picked from those in the workspace.

### 4. Data sources: what qrlab downloads, and what you download

The rule, from CLAUDE.md, is that the terms of a source are checked and recorded before it is
added. A first look on 2026-11-15:

| Source | Terms, first look | Decision |
| --- | --- | --- |
| ECB, Kenneth French, Open Source Asset Pricing | already reviewed | downloaded by qrlab, as today |
| iShares (BlackRock) | personal, non-commercial use. BlackRock's US iShares terms forbid robots and automated copying; the UK and EU terms must be read in full | downloaded by you, by hand; qrlab imports the file (8.2b) |
| Vanguard (Europe) | personal, non-commercial viewing and download; reproduction needs written permission | downloaded by you, by hand; qrlab imports the file (8.2b) |
| Exchange prices (Borsa Italiana, Xetra) | no clear terms for free history downloads found | not added. Prices come from the issuer's NAV history, downloaded by you |

So 8.8 adds **no new automatic source.** A price fetcher for a licensed API, with the user's
own key and its terms recorded, goes to `docs/IDEAS.md`.

**8.2b, the iShares and Vanguard file mappings,** needs one real public file per issuer to
learn its layout: a holdings file and a NAV history. You can download them by hand, or I
download them with your explicit OK, naming the file, the source and the size. Only a
synthetic file with the same layout is committed; the real ones stay in `data/` (git-ignored).

## Edge cases

- **An empty portfolio:**
  - no transactions: Validate says so, and Create report is disabled;
  - transactions but no prices: the report runs and says the value is unknown, as today.
- **Wrong rows:**
  - a duplicated `id`, or a sale of more units than held: raised by the library, shown with
    the row;
  - an ISIN missing from the instruments table: an error naming it;
  - a missing currency: an error.
- **Rows entered out of order** are sorted by date when saved, and ties keep their entry
  order. The file is always written in ascending order.
- **Decimals:**
  - a comma typed as decimal separator is refused, with a hint; it is never guessed;
  - values keep their exact decimal text.
- **An existing `portfolios/<name>`** is never overwritten; the name must be new.
- **A config written by Create report** that already exists is not replaced without a
  confirmation.

## Tests, hand-calculated first

- **Round trip.** A buy of 10 units at 50.00 EUR with a 2.00 fee is written and read back to
  the same `Transaction`, so the cost basis is 502.00. The written bytes are pinned.
- **The native format gives the same report as the mapped one.** The synthetic broker export
  in `examples/data/` is converted to native. The report run on it gives CSV outputs identical
  to the mapped run.
- **Starting position.** 100 units at a cost of 40.00 and a price of 50.00 give a value of
  5,000.00 and an unrealised gain of 1,000.00. TWR starts on the start date.
- **Kind parameter.**
  - A missing `transactions_format` raises with the hint.
  - `"native"` together with a mapping raises.
- **App view model,** without Qt:
  - add and edit rows;
  - only the fields a kind uses are editable;
  - Validate returns errors with row and column;
  - Save writes rows in ascending order;
  - Create report writes a config that `validate_experiment` accepts.
- **App self-test:** it opens the Portfolio screen.
- **Byte identity:** examples and studies are unchanged, apart from the one added line in the
  mapped configs.

## Risks

- **Scope.**
  - The table editor is the largest new piece of app code.
  - Keep to one table per file: no charts and no drag and drop.
  - Further ideas go to IDEAS.
- **Real data in the repository.**
  - The app writes only inside the workspace the user opens.
  - A test checks that no file under `tests/`, `examples/` or `configs/` comes from a
    workspace's `portfolios/` folder.
- **Breaking configs.** The new required parameter changes the existing report configs, the
  example configs and the app template, all in the same change.
