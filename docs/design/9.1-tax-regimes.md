# Design note — Phase 9.1: tax regimes as a common shape

Status: **approved 2026-11-15, presets in 9.2.** Deviations, if any, are listed at the
end. First phase of Level 9 (`docs/design/level-9-plan.md`).

## Goal

Adding a country must mean writing its rules, nothing else. Italy moves behind the common
shape **unchanged**: every Italian output, report and number stays byte-identical.

## What ties the code to Italy today

1. **`qrlab.tax.italy`** returns a `TaxPosition` whose fields are Italian: the regime
   (amministrato or dichiarativo), the categories (*redditi di capitale* or *diversi*), the
   public-bond share and the four-year loss lots.
2. **The report kind** (`experiments/kinds/portfolio_report.py`):
   - reads `[parameters.tax]` with Italian keys only (`regime`, `public_share`);
   - builds the Italian tables itself (`tax_events.csv`, `losses_balance.csv`);
   - writes three Italian scalars.
3. **The report** (`reporting/portfolio_report.py`) has a hard-coded Italian section: the
   regime sentence, the dichiarativo estimate, the columns, the loss lots and the Italian
   sources.

## Design

### 1. One result shape: `qrlab.tax.TaxReport` (new module `qrlab.tax.regime`)

A country's result, described rather than coded:

- **`country`** (`"it"`), **`as_of`**, **`checked_on`** (the date its rules were checked);
- **`sources`**: one tuple per report language (`en`, `it`);
- **`paragraphs`**: label keys with their values. A value may be text, a date, an amount, a
  list of holdings, or another label key, so that each is formatted and translated by the
  report;
- **`tables`**: each a `TaxTable` with:
  - a file name (`tax_events`), a title key and an optional note key;
  - typed columns: a column key for the CSV, a label key for the report, and a kind (date,
    year, holding, label, text, money or share);
  - the rows, in exact `Decimal`s;
- **`totals`**: label key and amount pairs;
- **`scalars`**: the run record's numbers (Italy: `tax_due`, `tax_withheld`,
  `losses_remaining`).

The CSV tables and the HTML section are both written **from this shape alone**, by generic
code. A column's kind decides its formatting (money, percent, date, translated label), so a
new country adds no rendering code.

### 2. One interface: `TaxRegime`

```python
class TaxRegime(Protocol):
    country: str  # "it"

    def parse(self, table: Mapping[str, object]) -> object: ...  # its [parameters.tax] keys
    def report(self, inputs: TaxInputs, config: object) -> TaxReport: ...
```

- **`TaxInputs`** gathers what any country may need:
  - the ledger history and its transactions;
  - the instruments;
  - the valuation, which a wealth tax needs;
  - the converter and `as_of`.
- **`REGIMES`** maps a country code to its regime; 9.1 has only `"it"`.
- **Italy is unchanged inside.**
  - `italian_tax_position` and `TaxPosition` stay, as public API.
  - A new `italian_tax_report(position) -> TaxReport` describes today's tables, sentences and
    sources exactly.

### 3. The report kind

- `[parameters.tax]` gains a **required `country`**. The other keys are the country's, checked
  by its `parse`.
  - Italy: `country = "it"`, then `regime` and `public_share` as today.
  - A missing `country` raises with the list of countries.
- The kind writes the tax CSVs and scalars from the `TaxReport`, with no Italian code left in
  it.
- `build_portfolio_report(tax=...)` takes a `TaxReport | None` instead of a `TaxPosition`, a
  change to its public signature.

### 4. Projections and backtests: presets move to 9.2

The plan put per-country `TaxModel` presets in 9.1. I propose to add them in 9.2, with the
first country that differs from a flat gains rate:

- **Italy's projection taxes are already explicit:** the gains rate, and the loss rules of
  8.6b.
- **A preset wired into the report** would replace stated rates with implied ones. That
  needs its own design, with Switzerland's income term (plan, 9.2).

## Tests (hand-calculated first)

- **Italy unchanged.** The 8.6a hand cases (tax 260, the 300-loss balance to 2029) pass
  unchanged, with `country = "it"` added to the configs. The Italian report outputs are
  byte-identical to `main`'s:
  - `tax_events.csv`, `losses_balance.csv`, the scalars and `report.html`;
  - in English and in Italian;
  - for amministrato and dichiarativo.
- **The shape renders by itself.** A toy regime, defined in the test, with one table of each
  column kind and two paragraphs. Its CSV has the declared columns and values, and its HTML
  shows the translated labels and formatted values in both languages. No country code is
  touched.
- **Config errors:**
  - a missing `country` raises and names `"it"`;
  - an unknown country raises with the list;
  - the Italian key errors are the same as today.
- **Guards:**
  - the 8.7 message test covers any new message;
  - the API snapshot shows the changed signature.

## Edge cases

- **A country with no events:** the section shows its paragraphs and an empty table with
  its note, as Italy does today with no sales.
- **A `None` in a money column** (Italy's "not computed") becomes an empty CSV cell, as now,
  and the "not available" label in the report.
- **A table with no rows is dropped from the HTML** when the regime says so. Italy's loss
  table is shown only when there are lots, as today.

## Risks

- **Byte identity of the HTML.** The generic renderer must reproduce Italy's alignment,
  number formats and the place of each note. The test compares with `main` directly.
- **Over-generalising before a second country exists.** The shape covers what 9.2
  (Switzerland: yearly income items and a wealth-tax line) and 9.3 need, and no more.
  Anything else waits for its country.

## Deviations

- **`TaxRegime` declares its key names** (`keys`, `optional_keys`). The report kind checks
  them, as it checks every table, so the messages are the same as before. `parse` then reads
  the values.
- **Each column states its alignment.** Italy's losses table right-aligns its date
  ("usable until"), while the events table left-aligns its date. A rule by kind would have
  changed the HTML.
- **The totals are a table** written to the report only (`file = None`), with a label
  column and an empty header, as before. `shown_when_empty` keeps the losses table out of
  the HTML when there are no lots, while its CSV is still written.
- **A paragraph's values are in `args`.** A field called `values` is mistaken by the linter
  for pandas' attribute.
- **Byte-identity check.** Eight Italian runs, run with the code of `main` (without
  `country`) and of this branch, give identical outputs and scalars: `report.html`,
  `tax_events.csv`, `losses_balance.csv` and `check_findings.csv`. They cover:
  - amministrato and dichiarativo;
  - Italian and English;
  - a withheld tax equal to or different from the tax due.

  Only the config hash differs.
