# Design note — Phase 7.4: several currencies and look-through in the `portfolio_report` kind

Status: **approved 2026-11-14.** Deviations, if any, are listed at the end. Last of the
gap-closing phases (see 7.1).

## The problem

The library can already do both of these things:

- **Several currencies.** `EcbConverter` converts with dated ECB rates and records every rate
  it carries forward. The report shows the FX source and the stale rates.
- **Look-through.** `look_through`, `LookThroughInputs` and tracking series feed the
  look-through section of the report and nine health checks: country, sector, issuer, pair
  overlap, duplicated exposure, tracking difference, tracking error, tracking difference
  against TER, and stale holdings.

The `portfolio_report` kind is what the CLI and the app run, and it uses neither:

- every amount and price must be in `base_currency`; a USD dividend or a USD cash balance
  raises `CurrencyError`;
- it passes `lookthrough=None`, so the look-through section says it was not done, and the
  look-through and tracking checks never run.

So the report that people actually get is weaker than the one `examples/portfolio_report.py`
builds in Python.

**The obstacle: a variable number of files.** There is one price file per currency, because a
price mapping has one currency, and one holdings file per fund. A kind declares a fixed list of
input names today, so it cannot take "one file per fund".

## Plan: two steps, each on its own branch and merged after your OK

### Step 7.4a: groups of inputs, then several currencies

1. **Groups of inputs in the config** (`qrlab.experiments`).
   - An input may be a table of files with free keys. For example:
     ```toml
     [inputs.holdings]
     IE0000000012 = "../data/holdings_world.csv"
     IE0000000020 = "../data/holdings_em.csv"
     ```
   - Each file is flattened to the name `holdings.IE0000000012`. It is resolved, checked to
     exist, hashed before and after the run, and listed in `record.json` like any other input.
     Every file therefore stays in the record with its SHA-256.
   - A kind declares which names may be groups, with a new field
     `ExperimentKind.input_groups: tuple[str, ...] = ()`.
   - The rules:
     - a table under any other name raises;
     - a group must have at least one file;
     - keys must be non-empty and contain no dot.
   - This is an addition with a default. Existing configs and kinds are unchanged, and
     `RECORD_FORMAT` stays 1, because the record only gains input names.
2. **Several currencies in `portfolio_report`**, all optional:
   - **The `fx` input:** the ECB `eurofxref-hist` zip, for example the file already in
     `data/raw/ecb/`. Its provenance comes from the raw store's sidecar when there is one,
     checked against the file's SHA-256, as the studies do.
   - **The `fx_max_age_days` parameter:** required when `fx` is given, refused otherwise. It is
     the oldest acceptable rate, in calendar days.
   - **The groups `extra_prices` and `extra_prices_mapping`:** one price file and mapping per
     extra currency, under the same keys (e.g. `usd`). The two groups must have the same keys.
     An ISIN in two price files raises.
3. **Behaviour.**
   - **Without `fx`:** as today. Foreign amounts raise with the same message, which now adds
     "give an fx input".
   - **With `fx`:** `EcbConverter(base=base_currency, max_age_days=fx_max_age_days)` is used
     for the ledger replay, the valuation, the checks and the report.
     - The report's FX line says "ECB reference rates, max age N days" instead of "EUR only".
     - Its existing table lists every carried-forward rate.
     - The provenance list gains the FX file and the extra price files.
4. **Hand-calculated test.**
   - The data:
     - EUR base, EUR/USD at 1.25 on the valuation date;
     - 10 shares of a USD-priced fund at 100 USD;
     - 250 USD of cash;
     - 1,000 EUR of cash.
   - The values: the position is 10 × 100 / 1.25 = 800 EUR, the USD cash is 250 / 1.25 =
     200 EUR, and the total is 2,000 EUR.
   - With a GBP base and EUR/GBP at 0.8, the same total is 2,000 × 0.8 = 1,600 GBP, through the
     cross rate via EUR.
   - A rate one day old with `fx_max_age_days = 0` raises. With 1, it is used and listed as
     stale.

### Step 7.4b: look-through and tracking

1. **Holdings, all optional, keyed by fund ISIN:**
   - the groups `holdings` and `holdings_mapping`, with the same keys;
   - per fund, `[parameters.holdings.<ISIN>]` with `as_of`, `weight_basis` and
     `sector_taxonomy` (text, or `"none"` for no taxonomy). These are explicit, because
     `parse_holdings_csv` needs them and they cannot be guessed from the file.
   - `lookthrough_treatment`: `"as_reported"` or `"normalised"`. Required when `holdings` is
     given, refused otherwise.
2. **Tracking, optional, keyed by fund ISIN:**
   - the groups `tracking` and `tracking_mapping`. Each file is a price CSV with its mapping and
     exactly two columns:
     - one whose instrument id is the fund's ISIN: the fund series, which must be NAV or total
       return;
     - one other: the index series, which must be total return.

     The existing `tracking_difference` rules check these types.
   - The fund's hedge currency comes from the instruments file (`hedged_to`). The index's comes
     from `[parameters.tracking.<ISIN>] index_hedged_to`, a currency code or `"none"`.
   - A tracking file for a fund that has no holdings is allowed: tracking does not need
     look-through.
3. **Behaviour.**
   - The kind builds `look_through` on the last valuation date, from the check context's
     position and cash weights. It wraps the result in `LookThroughInputs` and passes it to
     the checks and to the report.
   - Holdings dated after the last valuation date raise (look-ahead), as `look_through` already
     does.
   - A holdings file for a fund not held is refused, because it would silently not be used.
   - New scalars, tagged `descriptive`: `lookthrough_funds` and `unexplained_weight`.
4. **Hand-calculated test.**
   - The data:
     - the fund is 60 % of the portfolio, cash 40 %;
     - its holdings are 40 / 25 / 20 / 14 % (sum 99 %), as in `examples/portfolio_report.py`.
   - As reported: the exposures are 24.0 / 15.0 / 12.0 / 8.4 %, the unexplained weight is
     0.6 %, and cash is 40 %.
   - Normalised: the exposures are 60 × w / 99, and nothing is unexplained.
   - The report matches the one `examples/portfolio_report.py` builds from the same data, so
     the kind and the Python example are checked against each other.

### Examples

- The existing `example_portfolio_report.toml` and its output stay unchanged.
- A new `example_portfolio_report_full.toml` uses synthetic files (made-up ISINs) in
  `examples/data/`:
  - a USD fund with USD prices;
  - a synthetic ECB-format FX file;
  - one holdings file;
  - one tracking file.

## Compatibility

- **Additions only:** `ExperimentKind.input_groups`, input tables in configs, and new optional
  inputs and parameters. Every key that is new and required is required only when its
  optional input is given, so existing `portfolio_report` configs run unchanged.
- **Byte identity:** the example `portfolio_report` output is checked byte for byte against
  the current one, and studies 1 and 3 are re-run.

## Tests (besides the hand-calculated cases)

- **Input groups:**
  - flattening, hashing and the record;
  - a group under a name that is not a group;
  - an empty group;
  - a key with a dot;
  - a file changed during the run (the existing check);
  - `qrlab kinds` lists the groups.
- **FX:**
  - `fx_max_age_days` without `fx`, and `fx` without it;
  - mismatched keys between `extra_prices` and `extra_prices_mapping`;
  - an ISIN in two price files;
  - an FX sidecar whose hash does not match;
  - a GBP base.
- **Look-through:**
  - mismatched holdings keys;
  - a fund not held;
  - holdings dated after the valuation;
  - a missing `[parameters.holdings.<ISIN>]`;
  - a tracking file without the fund's column, with a price-only fund series, or with a
    non-total-return index.
- **Checks:** the look-through and tracking checks now run, with findings in
  `check_findings`.
- **Template and app:** `config_template` shows the groups as commented tables. The app's
  smoke test runs the full example.

## Out of scope (stays in `docs/IDEAS.md`)

- Risk and projection sections in the kind (`risk=None`, `projection=None`).
- A benchmark series for the relative checks.
- An issuer map for look-through (`issuers=None`): issuers stay securities.
- Downloading FX from the kind. The kind only reads a local file; `qrlab fetch` remains an
  idea.

## Risks

- **Scope.** This is the largest of the four phases, which is why it has two steps, each
  tested and merged on its own.
- **Config complexity.** Per-fund parameter tables are verbose. That is the price of not
  guessing holdings dates and weight bases. The full example shows the whole shape.
- **Real data.** Real broker exports, issuer holdings and FX stay in `data/`. Tests and
  examples use synthetic files only.

## Effort

About 4–5 h for 7.4a and 4–5 h for 7.4b.

## Deviations

### 7.4a

- **Two more optional `ExperimentKind` fields.**
  - `optional_parameters` makes `fx_max_age_days` visible in `qrlab kinds` and in the
    templates.
  - `check_inputs(parameters, input_names)` runs at validation, so "required with `fx`,
    refused without it" and "the two price groups need the same keys" are caught before a
    run, not recorded as a failed run.
  - Both have defaults, so other kinds are unchanged.
- **A wider hand-calculated case.** Besides the case of the design (2,000 EUR and 1,600 GBP),
  an extra-price-file case adds a EUR fund (2,500 EUR). The full example is checked by hand
  too: 15,482 EUR.
- **Valuation dates.** They are the union of the dates of all price files from the first
  transaction on. With one price file, this is the same set as before.
- **Byte-identity check.** The `portfolio_report`, `risk_report` and `backtest` examples were
  run with the code of `main` and of this branch on the same input files, and
  `packaging/compare_runs.py` reports them identical. Studies 1 and 3 were re-run, also
  identical.
- **`*.zip binary`** was added to `.gitattributes` for the synthetic FX file.
- **App smoke test.** Running the full example in the app's smoke test moves to 7.4b, when the
  example also has look-through.

### 7.4b

- **`exposures.csv`.** Besides the two scalars of the design, the run writes the look-through
  rows as a table, tagged `descriptive`, so the exposures can be read without the HTML report.
  This also lets the tests compare the kind with `look_through` called directly.
- **Tracking for a fund not held** is refused too, like holdings. Tracking checks on a fund the
  portfolio does not hold would describe nothing in it.
- **Tracking series are checked when read.** The kind calls `tracking_difference` once, so a
  price-only fund series, a non-total-return index or a currency mismatch fails the run with
  the library's message instead of failing inside a health check.
- **The tracking hand case is a tracking difference.** The four monthly dates of the example
  are less than a year, so the TD is shown over the period (-0.09 %, by hand) and not
  annualised. The tracking checks then state that no held fund has a year of data, which the
  test checks too.
- **A new ISIN for the example's USD fund.** In 7.4a the full example's USD fund used
  `US0000000119`, which is also a security in the world fund's synthetic holdings. With
  look-through the same code would have meant two things, so the USD fund is now
  `US0000001000`. The 7.4a hand calculation is unchanged (15,482 EUR).
- **Byte-identity check.** The `portfolio_report` and `scenario_analysis` examples were run with
  the code of `main` and of this branch, and `packaging/compare_runs.py` reports them identical.
  Studies 1 and 3 were re-run, also identical.
