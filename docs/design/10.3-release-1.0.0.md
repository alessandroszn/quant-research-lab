# Design note 10.3 — release 1.0.0

Status: **approved 2026-11-16, with the recommended choice for decisions 1 and 2.** Third and last phase of Level 10
(`docs/design/levels-10-13-plan.md`). It follows the owner's two decisions in 10.2:

- **E-mail, option A:** rewrite the history with the `noreply` address, then publish it in a
  new repository with the same name. The old repository is renamed and stays private.
- **Personal passages:** the three passages neutralised in 10.2 are replaced in every past
  version too.

## Why

The repository can become public only once its history is clean. After that, 1.0.0 goes out
as `releasing.md` says: first a release candidate on TestPyPI, then the final version on PyPI,
with the docs and the Windows installer.

- **The passages:** every past version holds the old wording **exactly**, as it is saved in
  `data/publication/replace-text.json`. A search of the whole history found them in no other

- **The tags:** the four old tags contain only `ci.yml`, which runs on pushes to `main` and on
  PRs. So pushing them starts no workflow.
- **The package name:** `quant-research-lab` is free on PyPI and on TestPyPI (404 on both).

## A finding: commit hashes cited in the docs

The experiment runner records the code version, and the docs cite it:

- the four study pages, the working-paper note and the CHANGELOG cite `63f808a`, the commit
  the studies ran on;
- `docs/paper/_generated/values.json` holds it four times;
- the 10.1 note and the Level 10–13 plan cite `e729101` (the last green CI) and `2b06310`.

The rewrite changes every hash, so these would point at nothing. `63f808a` is older than the
three notes, so its rewritten twin has **exactly the same tree** (same tree hash, checked).

**Proposal:** one commit after the rewrite replaces each cited hash with its new twin. A
sentence in `releasing.md` and in this note's results records the date of the rewrite and the
rule: "every commit kept its tree, except the 55 whose files held a personal passage". The
map of old to new hashes stays in the git-ignored `data/publication/`, because the old hashes have
no meaning in public.

## Decisions for the owner

1. **The tool.** I recommend `git filter-repo` 2.47.0 (2024-12-04), the tool that git's own
   manual recommends in place of `filter-branch`. It is used only as a tool, not added to the
   project:
   - **Download:** `git_filter_repo-2.47.0-py3-none-any.whl`, 76 KB, from PyPI, run with
     `uvx --from git-filter-repo==2.47.0 git-filter-repo`.
   - **Why it is better here:** it rewrites tag objects, so it changes the taggers in the
     same pass. With `filter-branch`, the four tags would keep the personal tagger and would
     have to be re-created by hand.
   - **The fallback,** if you prefer no download: `git filter-branch`, built into git, plus
     re-creating the four tags by hand with the same messages and dates. More code of my own,
     so more to verify.
2. **`#N` in the 66 merge subjects.** In the new repository, `#12` would link to a future,
   unrelated issue 12.
   - **Recommended:** rewrite only the prefix `Merge pull request #N from` to
     `Merge pull request N from`. GitHub then makes no link, and the number still matches
     the PR in the private archive.
   - **Alternative:** leave the messages unchanged.
3. **The release candidate keeps the name `1.0.0rc1`.** It was prepared on 2026-11-13 but
   never tagged or published, so no version number is skipped. The *Unreleased* entries
   (Levels 8–10) move under `[1.0.0rc1]`, with the date of the tag.

The checkout is moved at the end, so it stays as it is until the new repository is

- **`main`:** reset to the rewritten `main`. The trees are equal, so no file changes, and
  untracked files (`AGENTS.md`, `data/`) are untouched.
- **Tags:** the four old local tags are replaced by the rewritten ones.
- **Old branches:** the 114 local branches still hold the personal address. I propose deleting

  deleting them means no `git push` can publish them by mistake.

## Risks

| Risk | Guard |
|---|---|
| An old branch or tag reaches the public repository | Only the clean clone pushes, by name; old branches deleted in I |
| The rewrite changes a file it should not | Per-commit tree comparison (C.2); final tree hash equal |
| A passage survives in a form not matched | Every past version holds it exactly (checked); search over every blob after the rewrite |
| Results lose their link to the code | Cited hashes updated; trees unchanged, so each result's code is byte-identical |
| The old repository's PRs still show the history | It stays private, renamed; only the owner can read it |
| A workflow publishes by itself | Every publish waits in a protected environment for the owner |
| Something goes wrong mid-way | The bundle, and the untouched working checkout until step I |

## Out of scope

- Any change to the library or the app; any new dependency of the project.
- Announcements of any kind.
- Deleting the old repository: it stays as the private archive.
